# 连续执行与可见通知标准 V3.29.0

本标准解决长批次中“看起来停了、百分比到了 100% 却没有说明、用户说继续后又重复确认”的执行歧义。它不改变课程正文结构，也不扩大用户授权范围。

## 0.0 课程级固定进度入口

- 用户要求“实时进度写一遍、点链接就够了”时，唯一应交付的长期链接是 `outputs/<课程名>/99-处理记录/00-实时进度.md`；该页再链接当前批次详细页。
- 批次切换只更新固定入口的当前批次和相对链接，不创建新的用户入口、不要求用户重新保存链接。批次页可继续作为内部审计明细，但不主动重复发送。
- 进度写入器每次刷新批次页时同步尝试刷新固定入口；固定入口刷新失败不能伪造成功，也不能中断正在运行的课程，必须把批次页作为回退并记录异常。

## 0.1 自动续接静默分支（最高优先级）

- 由目标模式、心跳或系统自动续接触发的轮次，只有现场确认真实执行者仍在推进、且没有等待 Codex 完成的审读/修复/发布动作时，才可只检查状态并静默结束。静默是通知规则，不是停止生产的授权；不得重复发送“仍在运行”“入口不变”“模型继续生成”等同义消息。
- 下一步需要 Codex 推理时，在当前会话继续完成，不得结束会话等心跳再做一步；下一步属于已授权机械流程时，用阻塞式连续执行器接续。定时任务只做异常探测，不能冒充生产执行者。当前会话结束后不会自动继续 Codex 推理，必须如实记录这个边界。
- 静默不得通过发送空白回复、单独标点或占位文本实现；否则客户端仍会显示一条消息气泡，必须直接结束内部轮次。
- 用户主动提问或明确要求查看时才允许回复，且单链接模式下只引用既有 `progress_link`；链接失效才创建新链接并说明原因。
- 自动续接、跨对话恢复和心跳都必须读取 `notification-state.json`。事件键相同即静默，不因新线程/新轮次重发。
- 已产生的历史消息不能撤回；本规则从下一次自动续接起生效。只有完成交付、明确异常或需要用户决定时才恢复可见通知；进入发布阶段本身只更新进度文件。

## 0. 单一进度链接模式（用户明确要求时强制启用）

- 用户说“实时进度写一遍、点链接就够了”或表达同等意思时，每批只保留一个 `00-实时进度.md` 链接。启动时交付一次；之后心跳只更新文件，不发送重复的助手消息。
- 在 `work/<run-id>/notification-state.json` 保存 `last_notified_event_key`、`progress_link`、`last_notified_at`。事件键由 `run_id + event_type + lesson + phase + completed_units + batch_status` 组成；事件键不变时严禁再次通知。
- 自动续接、目标模式心跳、进程轮询、模型 token 增长和“状态仍为 running”都不是通知事件。用户没有要求主动提醒时，保持静默，只让同一链接可读取最新状态。
- 启动入口只交付一次；主动通知仅限完成交付、明确异常/恢复或需用户决定。课时内部完成、普通阶段切换、生成100%都只更新固定页并继续生产，不额外弹消息。没有变化时不发送“仍在运行/入口不变/模型继续生成”等同义句。
- 跨对话恢复先读通知状态；已通知过的事件不重发。通知状态文件丢失时先补写并去重，不能以新对话为由重复刷屏。

## 1. 继续指令的处理

- 用户说“继续”“下一批”“开始第 N 批”，且上一批次的课程、范围和授权仍明确时，先读取真实 `run_status.json`、`batch_state.json`、`heartbeat.json` 和阶段产物，再直接恢复或启动；不要重复询问已经确认过的模型、课程和批次范围。
- 若存在正在运行的同一批次，只监控并续接，不另起第二个进程；若状态已完成生成但尚未发布，继续发布验证；若已到人工验收，先交付真实文件，不把“继续”解释为跳过验收。
- 若发现课程名、来源范围或授权发生变化，暂停并只询问会改变结果的那一个选择。

## 2. 三个实测集合与当前阶段

用户可读进度页和关键通知都要分别写出：

1. **证据就绪**：现场核验冻结来源/资产的精确课时集合，不按文件存在统计。
2. **Codex定稿并独立复核通过**：绑定当前稿指纹的独立复核通过集合，不把七项齐算入。
3. **正式发布**：正式路径已验证并实际重开的集合，不把暂存算入。

三个集合各用本批同一分母；附当前课时、阶段、责任方、下一动作和最近真实产物。单工具旧状态不能制造外部证据就绪数。双工具字段和收据口径见[机械证据标准](dualtool-mechanical-evidence-standard.md)。

每个100%只说明对应集合齐全，不代替用户验收和六层完成。全部复核通过却未发布即接续发布自检，不发送“还在处理”消息，不等心跳再走下一步。

## 3. 必须通知的事件

发生以下事件时主动通知一次；状态未变且没有新的成功事件时不重复刷屏：

- 启动预检通过后一次交付固定链接；
- 批次发布验证通过并交付实际文件、进入人工验收；
- 连续心跳异常后的恢复、模型窗口拆分或明确失败。

要求人工验收时，同一条消息必须附上一个实际可打开的 `01-逻辑稿.md`，并逐项给出该课七项文件；没有这些文件只能说明“尚未到验收阶段”。

## 4. 停止、卡住与恢复口径

- 每次心跳刷新进度页中的最后心跳时间、真实成功事件和下一检查点；页面不刷新时以心跳文件和真实 PID 为准。
- 连续两个心跳周期没有更新，先检查子进程、模型服务、最近阶段产物和日志，再决定恢复；不能仅凭“进程还在”说正常，也不能仅凭对话安静说已完成。
- 进程退出但批次未进入 `published_verified` 时，报告“异常停止/待恢复”，从最近有效断点继续，不重做已验证课时。
- 任何失败都保留原因和断点；不发布残缺稿，不把旧报告或空目录当成果。

### 4.1 生成完成后的即时自检（不等心跳超时）

每次恢复或一个阶段结束时，现场读取批次清单、暂存包、独立复核结论、正式目录和固定进度页，并记录：预期课时 ID 集合、已复核集合、已正式发布集合、冻结版本/指纹、当前阶段、责任人、最近成功事件与下一项可验证动作。数量相同仍须比对精确集合，不能把暂存 11/11 写成正式发布 11/11。

- 若预期集合均已复核、正式发布数却未达到预期，立刻从 `generation_complete` 转入发布自检；即使 PID、心跳或暂存文件仍有变化，也不得称“没有卡住”。Codex 负责接管证据后的正式定稿、发布与验证；外部工具的 `ready` 只代表证据可接管。
- 发布自检要先判断所选发布器会否覆盖旧课程索引、课件及手工修订；有风险时先做仅写 `work/` 的彩排和可恢复备份，不得为了推进百分比直接运行。
- 如果下一检查点仍没有正式发布或明确的彩排/修复产物，标记 `suspected_stall` 并查原因；连续两个心跳周期仍无可验证推进，标记 `blocked` 或 `failed`，写明失败命令、退出码、负责人和恢复断点。不得一直把同一个 0% 页面标为 `running`。
- 固定进度页必须同时显示“暂存/复核”和“正式发布”两种计数、当前卡点、下一动作及是否需要用户决定；只更新同一链接，状态不变时不重复发聊天消息。
- 发布验证通过才写 `awaiting_human_acceptance`。此时给出真实文件供用户阅读；未得到本批验收，不启动下一批。

## 5. ETA 与收尾

- 前两节没有完整实测前写“暂无法可靠预估”；之后只给范围，并说明依据是已完成课时的实测耗时。
- 批次完成通知必须区分“生成完成、发布验证完成、等待人工验收”三个事实。
- 整门课程只有在六层终检、课程级资产、最终入口实际重开和用户验收均完成后才可写 `course_complete`。
