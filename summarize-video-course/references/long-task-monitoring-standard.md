# 长任务监控与恢复标准

长时间转写、批量知识整理和跨对话继续执行时读取本文件。目的不是让进程“看起来在后台”，而是让任务状态、实际进度、异常恢复和完成通知都能被证据验证。

## 一、把任务拆成两层状态

同时存在“课时状态”和“运行状态”时，不能把两者混成一句“完成”：

- **课时状态**：`pending`、`transcribing`、`screening`、`building_knowledge`、`complete`、`failed`、`awaiting_content_decision`。
- **运行状态**：`queued`、`running`、`checkpointed`、`suspected_stall`、`orphaned`、`awaiting_user`、`complete`、`failed`。
- 一个课时完成，不代表批次完成；一个批次完成，也不代表用户已经验收；目标课交付完成后启动的下一批，应建立独立 `run_id` 和状态文件。
- 回复用户前先读取状态文件和实际进程。项目文档、旧对话或计划只能作为线索，不能代替当前证据。

## 二、启动前的长任务硬闸门

启动前写入唯一的运行状态文件（推荐 `work/<run-id>/run_status.json`），至少包含：

```json
{
  "run_id": "唯一运行标识",
  "scope": "本次明确处理的课时或批次",
  "source_count": 0,
  "source_duration_seconds": 0,
  "phase": "queued",
  "started_at": "ISO-8601",
  "last_heartbeat_at": "ISO-8601",
  "last_completed_lesson": null,
  "active_pid": null,
  "monitor_interval_seconds": 300,
  "next_expected_checkpoint": "普通话描述",
  "completion_notification_required": true
}
```

- 先做本地模型健康检查：确认 Ollama 只监听 `127.0.0.1`、`OLLAMA_NO_CLOUD=1`，用一个极短的本地请求验证模型能返回；健康检查失败时不启动整批。
- 目标模式可用时，先创建目标并写明终点、验证条件、主动交付动作；目标模式不可用时，必须先告知用户限制并记录等价的本地运行状态，不能静默把普通后台进程当作目标模式。
- 启动后立即记录真实 PID、源视频基线、模型参数和下一检查点。不要只记录“已启动”。

## 三、心跳和进度判定

- 长任务每不超过 5 分钟更新一次 `last_heartbeat_at`；每完成一课、一个阶段或一次恢复，也必须更新。转写器无法产生分段中间文件时，仍由监控器写外部心跳，但要明确“没有可用的百分比”，不得伪造进度。
- 心跳至少记录：当前课时、阶段、已用时间、最近成功事件、活动 PID、下一预期事件。可额外记录 CPU/内存，但它们只是辅助证据。
- **进程存在不等于运行正常**；CPU 增加也不等于有可交付进展。只有状态心跳、阶段产物或成功事件能证明进度。
- 如果状态文件超过两个心跳周期没有更新：标记 `suspected_stall`，检查模型请求、子进程、文件锁、磁盘空间和最后产物；不得继续重复发送“仍在运行”而不调查。
- 如果进程消失但状态仍为 `running`：标记 `orphaned`，先核对是否已有完整转写或课时包，再决定从断点恢复；在核对完成前不得报告“后台仍在运行”。
- 如果状态已写 `complete` 但转写/FFmpeg 子进程仍存在：先清理并确认子进程退出，再进入发布验证；不能把残留进程当作无关现象。

## 四、对话连续刷新时的用户消息规则

- 不要每个对话轮次重复发送同一句“还在运行”。状态没有里程碑变化时，至少说明：已运行多久、最后一个真实成功事件、当前阶段、下一检查点和“尚未到验收阶段”。
- 用户问“完成了吗”时，先给结论：`已完成 / 仍在处理 / 疑似卡住 / 等待你的决定`；随后给证据。不能用“后台已启动”“有断点”“CPU 在用”单独回答完成与否。
- 没有新文件或新阶段时，不得发起验收，不得要求用户查看文件夹、`.cmd`、日志或批次报告。
- 完成通知必须主动发送，不等用户追问；通知中先给本批实际可读 `01-逻辑稿.md`，并在同一条消息逐项给出完整七项资料。

## 五、恢复与停止

- 预估时间应按本机实测速度给出，并区分机器活跃时间、自然经过时间和人工阅读时间。没有可靠累计计时就写 `null`，不能用最后一次恢复耗时冒充整课耗时。
- 未超过预计时间且心跳正常时，不因没有中间文件而重启；超过预计时间两倍或连续两个心跳周期无成功事件时，才进入疑似卡住调查。
- 修复前保留逐字稿、模型原始回复和状态文件；停止时写入停止原因和可恢复断点。不得用空白、逐字稿摘录占位或旧课资料伪造完成。
- 同一类故障只在首课建立兼容样本并验证，样本通过后恢复整批；恢复时复用已完成产物，不重做已验证课时。

## 六、完成与目标收尾

只有同时满足以下条件，运行状态才能写 `complete`：

1. 运行进程及其子进程已退出或被验证安全清理；
2. 预期课时全部进入 `complete`，七项结构、内容、来源、无媒体和路径隐私检查通过；
3. 源文件大小、修改时间或 SHA-256 与基线一致；
4. 正式输出已发布且最终链接被重新打开验证；
5. 同一条主动通知中给出实际可读文件和用户下一动作。

如果目标课完成后另起下一批，必须在状态中明确写成两个独立事实：`目标课已交付` 与 `下一批运行中（尚未完成）`。不能为了关闭一个目标而把后续批次写成完成，也不能让用户误以为整门课程已经结束。

## 七、模型阶段的时间上限与长输入降载

- 长课时的阅读层先使用有时间戳的首、中、尾压缩来源；完整逐字稿仍保留给知识点、案例和最终追溯，不得把压缩稿写成原始逐字稿。
- 每次本地模型调用必须设置上下文长度、输出长度和请求超时上限。默认单次调用不超过 30 分钟；超时或连接中断时保留原始回复、逐字稿和阶段状态，并将课时标为待修复。
- 分块生成知识点覆盖清单时，窗口大小根据知识信号密度动态选择，输出预算按当前窗口行数和字段长度计算；不能把用于简短分类的低输出上限沿用到长清单。只要模型以长度原因结束、缺少 `END_OF_COVERAGE`、最后一条不完整或解析后条目明显少于来源覆盖，就视为截断，不得把“完整前缀”冒充整个窗口。
- 单个窗口截断时只拆分当前失败窗口；已经通过的清单窗口、卡片、逐字稿和正式课时全部复用。默认 `COURSE_CARD_INVENTORY_CORE_LINES=auto`，人工固定窗口只用于明确的兼容回退。
- 发现输出预算过低后，应先修正配置并用当前课的一个真实分块验证，再从最近一个已通过检查点恢复。已完成转写、已验证清单分块和已完成课时必须复用，不能因为调大输出上限而整课或整批重跑。
- 连续两个心跳周期没有阶段产物时，先调查模型连接和子进程；调查后仍无可恢复进展才停止。安全停止必须清空 `active_pid` 并写明恢复检查点。
- 恢复时优先复用有效断点和已通过课时；不得用逐字稿摘录占位版发布，也不得重新处理已经验证完成的课时。
