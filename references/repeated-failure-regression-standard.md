# 反复漏项回归标准

本标准把近期实际交付中反复由用户补救的动作，变成生成前、发布前和交付前的固定门禁。它不是“发现问题后再提醒”，而是要求 AI 团队在交给用户前完成证据闭环。

## 一、生成前防漏清单

每个课时建立一份覆盖记录，逐项写明完成、排除或阻断原因：

1. **来源覆盖**：视频、字幕、PDF/PPT/Word、图片和电子书逐文件入清单；不能只处理看起来像正文的文件。每个来源必须有明确去向，课程名、课时号和输出目标必须从授权目录和清单确认。
2. **课时筛选**：导览、前言、平台教程、通知和致谢不硬凑知识点；保留筛选结论和逐字稿，正式知识课单独统计。
3. **画面知识**：根据逐字稿提示和候选帧筛选真正承载知识的画面。凡保留关键画面，必须同时完成：原图可打开、视频时间戳、本地 OCR（辅助文本）、视觉语义总结。表格、流程图、漏斗、思维导图和公式不得只交扁平 OCR；OCR 看不清的字词标“待核对”，图示关系不确定标“需人工核对”。没有知识画面也必须记录排除理由。
4. **复用表达**：完整扫描逐字稿中的公式、步骤、条件分支、模板、话术和总结口诀。发现结构时先写 `A+B+C`/步骤链/分支，再写适用场景、使用方式、例子、内容性质和来源时间戳；不得把空泛“未发现”当作扫描结果。
5. **案例重构**：每个独立案例至少写清主体/产品、原状和触发问题、问题分析、具体动作、结果、限制和可复用启发；行业/运营复盘还要补目标、初始问题、关键转折和数据口径。逐字稿残句只能放在来源摘录，不能冒充背景或动作。
6. **术语校正**：阅读层发现明确 ASR 错词时，依据画面文字、上下文或老师后续说法修正 `00/01/03/04/05`；`02-时间戳逐字稿.md` 永不改写。无法确认的词保留原样并标重点核对。

## 二、发布前回归门禁

- `media_index.json` 必须同时有 `reusable_expression_review` 与 `visual_review`；画面记录必须含 `ocr_text` 或明确 `ocr_status`，以及非占位的 `knowledge_summary`。
- `04-案例与金句.md` 必须能找到扫描结果、公式/结构和完整案例；出现“本课未发现”时必须附扫描范围与排除理由。
- `00-本课总览.md`、`01-逻辑稿.md`、`03-知识点卡片.md` 中涉及画面知识时，必须给相对图片路径和时间戳；不能只在 `05-质量问题清单.md` 里报告“以后补”。
- 逐课七项资料必须位于 `outputs/<课程名>/课时资料/<课时>/`，不能误发布到课程根目录、批次目录或只留在 `work/`。
- 批次清单与正式输出做精确集合比对：不得漏课、错课、重复课时；每课源指纹不变。
- 进度百分比只统计完整验证课时；`100%` 仍需继续发布验证和用户验收。失败必须同步到批次状态和同一实时进度入口，不能留下旧百分比假装未发生。

## 三、交付前 AI 团队责任

用户只承担高风险例外的阅读判断，不承担基础找漏。交付前按以下顺序执行并留下证据：

`覆盖清单 → 画面 OCR/语义 → 复用公式 → 完整案例 → 术语校正 → 七项验证 → 实际打开 → 单一进度链接交付`

任一环节失败时：

1. 只修复失败课时，不重做已验证转写；
2. 先在 `work/` 备份并修复，再重跑质量闸门；
3. 仍失败则明确写入失败原因和可恢复断点，禁止发布残缺稿；
4. 同一里程碑只通知一次，普通心跳只刷新进度文件，不刷屏；
5. 只有实际打开的逻辑稿和七项文件交付后，才进入人工验收。

## 四、交付后抽查

每次用户指出一个漏项，必须做两件事：

- 修正当前课时的正式文件、暂存副本、媒体索引和质量清单；
- 在本 Skill 的回归记录中新增对应失败模式和自动检查条件，避免只修当前文件而不修流程。
